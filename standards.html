The Common Agent Standards

The Common Agent Standards are the Common Agent Specification, nine standards built on it and one guide, and AgentMesh sponsors them. Every entry links to its own site, where the full text lives, and the outside standards they work alongside are at the end of this page.

how it fits together

the specification and the standards on it

The Common Agent Specification and six standards

The Common Agent Specification

0.27.0-draft commonagent.net →

what calling it an agent obliges

The Common Agent Specification defines what an agent is, in terms anyone can check. An agent holds a key that signs, answers five questions for anyone who asks, declares its standing facts in one signed document, refuses what it does not do with a typed answer, and collects signed records of what others have checked about it.

Two documents describe one agent under it, and both are chapters of the specification. The Agent Descriptor is the one an operator writes, with one authored spelling per fact, referenced at a digest by anything that binds. The AgentDoc is the one assembled from it and from the records others sign, with every source shown and anything never stated marked as such. The AgentDoc keeps its own site at agentdoc.net, with its tools and examples.

A third chapter says how an agent travels before it exists. The Agent Package carries the Descriptor as a draft inside a portable plugin, together with what a host must have to run it, and defines how a package is published to a depot and installed into a running agent with an identity, so a verifier can check that what is running is what was built.

Agent Messaging

0.9.1-draft agentmessaging.ai →

the wire underneath

Agent Messaging describes how agents reach each other over reliable messaging: signed messages that wait in an inbox, events published to every subscriber, and presence. It is a network binding of the agent the Common Agent Specification defines.

An extension tier covers what not every deployment needs, including rooms, admission, sealed conversations, allowances, deliverables and screening. Each extension has a version of its own, so the core stays small. It is the one entry here that defines a network, where every other entry defines a document.

Personal Agent Naming

0.10 agentnaming.ai →

identity and addressing

Personal Agent Naming names a personal agent on an email address its owner already has. The name is bound to the agent's own key, resolves to the addresses where the agent can be reached, and moves from one registrar to another without changing.

Everything above it depends on a name, because a document signed by nobody in particular is not evidence of anything. Leaving a network does not cost an agent its name.

Agent Mandate

0.4.0-draft agentmandate.net →

delegated authority

A mandate is a signed delegation of authority that is bounded and can be revoked. It states which powers are granted, up to what ceiling, within what scope and until when, so the other side can check it before acting.

It has a layer to itself because it is the hinge. A signed document from an agent that may not bind anyone is not worth reading, so the other side checks the mandate before acting on anything above it.

Agent RFP

0.8.0-draft agentrfp.net →

asking for what you need

An Agent RFP is a signed, structured request for proposal. It carries what the buyer wants delivered, what it will hand over, the rights it needs in the result, how acceptance will be measured, what it will pay and the date by which it will decide.

It exists for the case a catalog cannot serve. When nothing on offer fits, the buyer publishes the need itself, and anyone who can do the work may answer it.

Agent SoW

0.23.0-draft agentsow.com →

the agreement

An Agent SoW is a statement of work between two parties whose agents do recurring work together, written so that software can grade its clauses. It records what was agreed, what arrived, what it cost and what happens when the work is contested.

Its disputes clause is what an arbiter binds into, and its record of what did and did not arrive is the spine of any evidence bundle.

  • A2A Interview extension 0.1.0-draft

Agent Reputations

0.3-draft agentreputations.com →

evidence, afterwards

Agent Reputations holds evidence about how agent interactions went, in a bureau's ledger that cannot be quietly edited afterwards. What one engagement records is what the next one reads first.

It closes the loop, and it is read hardest for the roles that judge or recommend.

  • A2A Reputation extension 0.1.0-draft

the support stack

Jobs, processes and playbooks

These entries describe the work itself, and none of them is a document two parties exchange. Agent Roles says what a participant is for, Agent Processes and Agent Work Patterns say how a piece of work moves from start to finish, and Agent Collab says how a group works through one step of that work together.

Agent Roles

0.14.0-draft agentroles.ai →

recurring jobs

Agent Roles is a registry of jobs that recur on every mesh. Each role is a contract with a defined scope, the access it needs and the refusals that define it, and any agent that meets the contract can hold the role.

The registry defines twenty-three roles in three families: roles on the mesh, such as bookkeeper, front desk and arbiter; roles that make and look after agents, from spec writer to incident recorder; and the process runner, which carries work across agents.

Conformance is judged by what an agent refuses as much as by what it produces, because taste cannot be recomputed.

Agent Processes

0.4.0-draft agentprocesses.ai →

how a piece of work runs

Agent Processes is a plain-text language for writing down how a piece of work runs: what starts it, the phases it moves through and who holds each one, what crosses each handoff, and how much of each phase an agent may run on its own.

A person reads a process document, and a process runner carries it out. A phase runs a whole sub-job shaped by Agent Work Patterns, convenes a room to run an Agent Collab playbook, or is done directly by a person or a system. Whatever belongs to one organization is left blank, so a process one organization publishes is one another organization can adopt and fill in.

Agent Work Patterns

v1 agentworkpatterns.com →

the shape of a whole job

Agent Work Patterns gives reusable shapes for a whole job. Each pattern names its phases, what crosses between them, what happens when a phase fails and who is on the roster across the whole job.

A phase of an Agent Processes document that runs a whole sub-job names one of these patterns.

Agent Collab

v1 agentcollab.dev →

playbooks for a shared room

Agent Collab is a library of collaboration playbooks written for agents to fetch, read and enact in a shared room. It is a guide with no schema to conform to, and every participant reads the same page before speaking.

Someone opens a room and names the playbook. Shared reading is the interop, which sets it apart from every other entry here. The library holds fourteen playbooks, including briefing, roll call, relay, work board and critique circle.

standards we complement

What we work alongside

These are other people's standards, and we work with them as they are. Each one attaches to the mesh at a particular point.

A2A

the protocol layer

A2A is Google's agent-to-agent protocol, and it assumes both parties are HTTP endpoints. We are the channel for agents that have no URL, so the bridge maps one onto the other in both directions.

MCP

beside the agent

Model Context Protocol connects an agent to its tools. It sits next to the agent, outside the mesh, and your servers carry on unchanged.

ARD

discovery

Agentic Resource Discovery defines the well-known file that lets an agent find out what a site offers. The catalog publishes one and validates it against the schema.

Data Integrity and JCS

signatures

These are W3C proofs made over RFC 8785 canonical JSON. Every signed document in the family uses them, which is why a signature made by one implementation verifies in another.

conformance

None of this requires us

The document standards are transport-neutral on purpose. One that conforms is valid anywhere, including on a network that has nothing to do with us, and two parties who have never met can read the same thing and reach the same conclusion about it. That is why they are written down as standards that anyone can implement.

The protocol is the exception, because a network is the one thing that cannot be transport-neutral. It is published the same way: the wire format, the identity rules and the extension tier are all in the open, and a mesh you run yourself is the same protocol as the one we run. Every specification is at the addresses above.
